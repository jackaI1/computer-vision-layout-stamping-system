# Seal-stamping FMEA Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Demonstrate useful design/process FMEA with scored failure modes, actions and verifiable requirement/test links.

**Architecture:** Maintain a JSON risk register and a human-authored method document under `quality/`. Generate a linked Markdown register and validate scores, ownership, action evidence and traceability in CI. Keep application behavior unchanged.

**Tech Stack:** Existing Python 3.12, standard library, pytest and GitHub Actions.

**Spec:** User request; the design and constraints are recorded here. The user explicitly authorized implementation through merge without questions.

## Design and approaches

A handwritten table is easy to read but cannot detect broken mitigations. A spreadsheet duplicates the existing JSON requirements workflow. Use JSON plus generated Markdown to fit the existing traceability system and catch drift without adding dependencies. Scores describe current controls using a project-specific 1–10 rubric; occurrence is an engineering estimate, not measured field frequency. Do not claim residual risk reduction or professional approval from synthetic tests. Distinguish verified software actions from open manual/PQ actions.

## Global Constraints

- Work on `skills/auto-fmea` in the supplied linked worktree; never push main.
- Public synthetic fixtures only; no secrets, seals or client drawings.
- Preserve application behavior; run the entire existing suite and new tests.
- Update README Skills demonstrated, requirements, traceability, IQ/OQ, change control and CI.
- Push, create the requested PR, wait for green CI, squash merge and delete remote branch.
- Write the requested result JSON outside the repository after verifying merge.

## Review Focus

- Invalid score types (including booleans), bounds or missing rationale must fail validation.
- Deleted/unrelated test evidence, unknown requirements and duplicate IDs must fail validation.
- Empty actions, invalid status and missing owner must fail validation.
- Low RPN must not hide high severity; stale generated reports must fail CI.
- Open operator checks must remain visibly open; characterization tests must not imply risk elimination.
